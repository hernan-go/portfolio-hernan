# Professional audit — 2026-10-10

Historical record of the complete Codex-assisted audit delivered before Iteration 0. Its content, priorities, results and limitations are preserved; local links are relative so they remain usable in the repository, and their labels retain the cited line numbers. This is neither a new audit nor authorization to make changes. Subsequent status is maintained in [PROJECT_STATE.md](PROJECT_STATE.md), and the owner's planning is recorded in [ROADMAP.md](ROADMAP.md). Code inspection, command checks and browser observations were performed with Codex assistance; they are not represented as independent human verification.

---

**The audit is complete. The portfolio has a solid technical foundation and a coherent identity; no grounds for a redesign were identified.** The best-supported improvements concern accessibility, adaptation to narrow screens and presentation of technical evidence for hiring.

No P0 issues were identified within the audited scope. Several bounded P1 issues were confirmed. Performance requires additional measurements before larger optimizations can be justified.

**1. Executive assessment and scope.** The review covered code, data, configuration, documentation, assets and existing artifacts in the `hernan-go/portfolio-hernan` repository, as well as the [production website](https://hernangobulin.com/).

Presentation was inspected at viewports of 1440 × 900, 1024 × 768, 768 × 1024, 390 × 844 and 320 × 740. Checks covered navigation between sections, project selection in Work and LAB, and keyboard behavior in the transcript and Work CTA.

Local checks completed successfully:

| Check | Result |
|---|---|
| ESLint, without autofix or caching | No errors |
| Application TypeScript, without emitting files or incremental compilation | No errors |
| Vite configuration TypeScript, without emitting files or incremental compilation | No errors |
| Effective TypeScript configuration | Strict checks enabled with TypeScript 6.0.3 |
| Git at audit completion | `main`, clean working tree |

No builds, installations, audits that generate files, commits, pushes or deployments were performed. No report file was created during the audit because that phase prohibited file creation.

Two limitations are important when interpreting the results:

- The deployed JavaScript filename differs from the one in local `dist`. Browser observations refer to production; `dist` sizes are evidence from the existing local artifact, without a guarantee of exact equivalence.
- Lighthouse, Core Web Vitals, CPU/GPU usage and behavior with a real screen reader were not measured. No results are attributed to those tests.

**2. Current strengths.** The project organization is appropriate for its size. `sections` composes the main areas, `components` contains interactions, and `data` separates content from presentation. Further development does not require a more complex architecture.

Project types, identifiers and statuses help maintain consistency. The reviewed effects clean up observers, listeners, timers and animations. Searches over small arrays are immaterial to performance: introducing memoization here has no demonstrated benefit.

The implementation also includes considered decisions:

- Work describes **role, scope, technologies, services and context**. This provides more professional information than a screenshot gallery.
- Operations Hub is selected initially and demonstrates plugin development and operational integrations. It is a suitable choice for presenting technical work.
- Native buttons, `aria-pressed` states, semantic navigation, a `main` landmark, headings and definition lists are present.
- Work and orbit animations pause outside the visible area and respond to changes in `prefers-reduced-motion`.
- Audio does not autoplay, handles errors and provides a transcript.
- Preview containers reserve space through heights or aspect ratios, reducing a common source of layout shifts.
- Main images use WebP; icons and logos use SVG.
- The requested nonexistent route returned **HTTP 404**, accompanied by application HTML. The visual error page provides clear return options.
- The [README](../README.md) explains the portfolio's purpose, organization and local workflow.

The editorial aesthetic, monochromatic presentation and backpack, box and container metaphors form a recognizable visual language. They are not usability defects in themselves.

The accessibility basis is specific: [WCAG 1.4.10 addresses reflow at 320 CSS px](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [1.4.3 requires 4.5:1 for normal text](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), and [2.4.7 requires visible focus](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html). The [WAI-ARIA dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) describes expected focus and Escape handling. Prolonged automatic motion should be reviewed against [WCAG 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html).

This does not constitute complete WCAG conformance certification.

**4. Engineering, performance and SEO assessment.** The React architecture is sufficiently modular and maintainable. No issue was identified that would justify Redux, a routing library or an additional abstraction layer. Simple homepage/NotFound resolution is appropriate for a single-page experience.

TypeScript works correctly, and the effective configuration has strict checks enabled. The absence of an explicit `"strict": true` is not a weakness in this environment: its effective behavior was verified.

Vite configuration is small and understandable. The main dependencies have clear roles. No HTML injection, dynamic evaluation or credential storage was observed in the inspected application code. Reviewed external links use `rel="noreferrer"`. **The complete dependency tree was not checked against an advisory database**, so this does not certify the absence of vulnerabilities.

Available performance sizes provide context, but do not establish experience quality:

| Local resource | Approximate size |
|---|---:|
| Hero portrait | 76.8 kB |
| Initial Operations Hub screenshot | 75.2 kB |
| Lúmina Académica screenshot | 602.4 kB |
| CLAEC screenshot | 579.6 kB |
| Eight Work screenshots combined | 2.76 MB |
| Existing JavaScript in `dist` | 300.3 kB |
| Existing CSS in `dist` | 49.1 kB |
| Audio | 468.8 kB |

These are file sizes, **not compressed transfer sizes or measured initial loading**. Importing all eight screenshot URLs does not automatically download all of them. Mounting two images with the same URL does not imply two complete transfers either: the browser can reuse the resource, although element and logic duplication remains.

The portrait and initial screenshot have reasonable sizes. Full-page screenshots warrant evaluating dimensions and decoding cost: the deployed CLAEC image is 1200 × 9185 pixels. However, its height also supports the scrolling interaction; reducing it arbitrarily could degrade that functionality.

Useful tests for LCP, CLS and INP would include:

- Cold loading with constrained network and CPU, identifying the actual LCP element.
- Recording layout changes during font loading and project selection.
- An interaction trace while changing cases, playing audio and browsing LAB.
- Checking compressed transfer, caching and the resources actually requested.

Fonts use `preconnect` and `display=swap`, which are positive decisions. Self-hosting or preloading them is not recommended without first verifying their loading contribution. Fixed grain, blurs and persistent `will-change` declarations are candidates for a rendering trace, not demonstrated performance problems.

For SEO, the declared language matches the English content, and a title and description are present. `robots.txt` contains `User-agent: *` and `Crawl-delay: 10`, with no `Disallow` prohibition. The missing sitemap is a minor improvement for a single-URL website.

The initial HTML depends on JavaScript to present content. This adds a rendering dependency and excludes the details of unselected projects from the initial DOM. Google documents this processing in its [JavaScript SEO guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics). This does not automatically justify an SSR migration: access and indexing should be verified first. [Open Graph](https://ogp.me/) metadata can be added as a small improvement.

**5. Hiring assessment.** The Codex-assisted professional assessment is that the portfolio communicates **autonomy, experience with operational needs and product awareness**. This combination is valuable to companies that need to build and maintain useful solutions as well as interfaces.

The Hero has personality and a clear promise: “Software built for real needs”. Specialization appears in “Software Developer — Frontend & Product Systems”, although with much less visual prominence than the manifesto. The identity works; assessing role fit requires somewhat more attention.

A large CTA, downloadable CV or conventional introduction is not considered mandatory. If frontend hiring is the primary objective, greater prominence for React/TypeScript expertise would be worth evaluating while preserving the composition.

Work is the most convincing section. Operations Hub demonstrates custom development, integrations and a repository. CLAEC and Lúmina describe educational and commercial ecosystems, providing evidence of operational experience. Distinct roles make it clear that responsibility was not the same across all projects.

The main ambiguity is that **the profile presents software development with a frontend focus, but most visible cases demonstrate WordPress/Moodle/PHP platforms; LAB still provides limited verifiable evidence of React/full-stack applications.**

This does not diminish the value of existing projects. It limits what a company can conclude about experience in:

- Designing a React application beyond the portfolio itself.
- Frontend/backend integration and data modeling.
- Handling errors, permissions and operational flows.
- Architecture decisions and validation.
- Teamwork and the specific boundaries of individual responsibility.

FastWork acknowledges collaborators and the owner's contribution, which is appropriate. Supporting artifacts are missing. Discovery projects can remain at that stage: their value lies in explaining investigation and judgment without suggesting an implementation that does not yet exist.

There is also an editorial opportunity in the strongest cases: they describe **what was built**, but less about **the difficult decision addressed and what changed operationally**. Figures are unnecessary if unavailable. A verifiable qualitative outcome—unifying processes, removing manual steps or integrating payments—may be sufficient.

Contact provides email, WhatsApp, LinkedIn and GitHub without requiring visitors to listen to audio. That independence is well implemented. Preserving readability of these access points on narrow screens is the priority issue.

For an initial hiring review, the portfolio provides reasons to explore the work. Assessing depth in React/full-stack development would require additional evidence. This is a professional assessment, not a prediction of recruiter responses.

**6. Priorities and elements to preserve.** H1–H4 should be addressed first: they affect readability, navigation and access to specific actions. H7 should be investigated in parallel; access and indexing verification is more valuable than starting with a sitemap.

H6 and evidence of application development should follow. This is likely the improvement with the greatest impact on positioning for a software company. H5 allows animations to be preserved while adding control.

The following changes are not considered necessary:

- Redesigning the monochromatic or editorial identity.
- Replacing the backpack, boxes or orbit with conventional cards.
- Removing animations across the board.
- Migrating to Next.js, SSR or a CMS based on technology preferences.
- Adding global state management.
- Splitting every component or extracting every JSX block.
- Memoizing searches over eight projects.
- Updating dependencies solely to pursue recent versions.
- Adding technology proficiency percentages, invented metrics or unsupported seniority titles.

Small typography in some controls warrants attention, but small text does not automatically constitute a violation. The verified Work issue is its combination of size and contrast. Informational-text requirements should not be applied to purely decorative background words.

**8. Future PRISMA CRM integration.** Based on owner-provided context, PRISMA CRM can address the portfolio's most important evidence gap: demonstrating a production full-stack application using React, TypeScript, Node.js, Express and MySQL. **Its repository was not audited during this phase**, so those characteristics remain owner-provided context.

LAB supports adding it without rebuilding the section, but some details should be prepared:

- Use a dedicated identifier such as `prisma-crm`, separate from the institutional `prisma` in Work.
- Explicitly identify it as “PRISMA CRM — production management application”; keep the existing case identified as the institutional WordPress website.
- Use the existing `RELEASED` status and clarify actual operational use.
- Present the owner's role and responsibility, technologies, architecture and one or two representative flows.
- Add an actual screenshot prepared for publication, without identifiable personal or financial information.
- Distinguish repository, demo and deployed application access. The current `prototypeUrl` field, whose link is labeled “Prototype”, is not an appropriate designation for a production system.
- Review the selector with four projects. The horizontal grid has three fixed columns, and the desktop composition uses explicit dimensions and offsets; adding an entry requires visual validation, although this does not imply it will break.
- Evaluate selecting it as the initial LAB project if demonstrating full-stack capability is the primary objective.

Unlike Work, `LabProject` does not yet have dedicated technology or responsibility fields. A small extension can address this. `visualKey` is required, but it was not observed to determine the preview: adding a value there alone does not generate a different image.

The future entry should select representative CRM capabilities and explain the problem, the owner's contribution and the relevant decisions. This provides more value than an extensive list of every module.

**The repository remained unchanged at audit closure. The recommendation is to preserve the portfolio and correct specific issues while strengthening professional evidence. Further action remained subject to owner instructions; no improvements were implemented and PRISMA CRM was not added.**
